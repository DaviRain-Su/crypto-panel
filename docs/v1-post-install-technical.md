# V1 安装后运行验证技术契约

日期：2026-11-09。基线：`879a93b`。状态：实现与自动检查、原生窗口检查已完成；具体结果见 [V1 验收记录](v1-acceptance.md)。

## 0. 需求、依据与边界

商业与用户需求引用 [V1 产品规格](personal-apps-v1.md) 第 1–4 节：个人应用从自然语言需求走到实际使用；用户已授权补齐安装后验证，不新增商业验证结论。架构复用 [宿主集成契约](v1-integration-technical.md) 的同一 Manager、原生批准、执行 lease、UI 主线程和禁签名 API runtime。

本轮只补齐受管理的 ACP / Local API 个人应用安装及更新后的首页验证、设置保存后的重试与结果反馈。现有文件夹、zip、签名商店、钱包和 ACP 推理协议保持既有行为。不把运行验证当成安装许可、交易许可或数据业务正确性的证明。

## 1. 数据与接口

`agent.Plugin` 增加可选的 `verification` 元数据。它只描述当前进程中当前已安装包的最近一次验证，不持久化，不在重启后自动执行应用。

| 字段 | 类型与约束 |
| --- | --- |
| requestId | string；来自原生确认对应的 Installation.RequestID |
| packageHash | string；严格等于用户已批准包的摘要 |
| page | string；清单中第一个 navigation.page，不接受外部任意页面名 |
| status | string；仅 waiting_settings、running、passed、failed |
| code | 可选 string；宿主固定代码，不使用脚本或上游异常文本 |
| checkedAt | 可选 RFC3339 时间；一次检查结束时设置，等待和运行中无完成时间 |

宿主状态按应用 id 保存一条记录，并以记录身份及原子取消标记使旧工作失效。后台工作只读不可变的请求摘要与取消标记，结果通过 runOnMain 回写。删除、包变化、上下文变化或应用退出后，旧工作不能覆盖新结果。

内部接口：

- `beginInstallationVerification(job)`：仅在 Manager.Decide 返回 installed 后调用；绑定 requestId、packageHash 和第一页。无设置立即开始；有设置进入 waiting_settings。
- `verifyInstalledApp(id)`：原生界面的验证 / 重试动作，或设置成功保存后的自动验证。当前包必须匹配已批准摘要，且可用、启用、有第一页。
- `ApplicationSettingsChanged(id, success, clearedSecret)`：可选 HTTP 宿主通知；成功写入且没有清空秘密时验证当前已跟踪的安装。清空秘密进入等待配置；失败时只使旧结果失效，不能执行或误报通过。未实现该可选通知的旧宿主继续调用 ApplicationsChanged。
- 共享的禁签名页面执行器：复用 RefreshPage 的完整性、启用、页面声明、执行 lease 和新 runtime；验证额外绑定 expectedHash，禁止记录插件日志，执行前检查是否已失效。

不新增 HTTP 验证、批准、签名或广播端点。外部 agent 可从已有 GET /v0/plugins 读取安全状态，也可以继续显式 refresh。

## 2. 状态机

| 当前状态 / 事件 | 条件 | 结果与副作用 |
| --- | --- | --- |
| pending / installing | 尚未原生批准并提交成功 | 不创建可运行验证，不执行 JS |
| installed | 无设置 | running；后台执行第一页 |
| installed | 有设置 | waiting_settings；不猜测必填项，不执行 JS |
| waiting_settings / failed / passed | 保存成功且没有清除秘密，或用户点击验证 | 新一轮 running；清除旧完成时间 |
| 任意已跟踪状态 | 设置保存部分失败或清除秘密 | 旧结果失效；不自动执行；提示保存或重试 |
| running | 同 id 重复请求 | 合并，不重复执行 |
| running | JS 执行和页面 schema 检查成功，记录与包仍匹配 | passed；记录完成时间，只反馈宿主固定文案 |
| running | 模块 / JS / 页面 schema / 网络失败 | failed；固定 EXECUTION_FAILED；安装仍保持 installed |
| 可开始状态 | 禁用、无页面、执行正忙、摘要变化、容量满 | failed；固定原因代码；不启动未授权或错误版本 |
| 任意状态 | 卸载、包变化 | 取消并移除旧记录；更新成功后只跟踪新的批准摘要 |
| 任意状态 | 网络 / 宿主上下文变化、退出 | 取消旧记录；迟到结果不写回 |

设置清单没有 required 字段。有设置项时始终提供“验证首页”，允许用户显式跳过可选设置；完整保存且没有清除秘密时也启动验证。清除秘密后等待重新配置或用户手动验证。禁用应用不因验证而自动启用。

## 3. 常量、错误与资源

同时最多 5 个安装后验证工作，不建立无限队列；与 UI/API 共享每应用一个非阻塞 lease。重复点击同一运行中记录不增加工作。每次使用新 runtime，沿用 JS 30 秒执行上限、256 MiB 内存及既有 fetch / RPC 限额。

状态代码仅使用宿主枚举：APP_BUSY、APP_DISABLED、NO_PAGES、APP_NOT_FOUND、CONTENT_CHANGED、SETTINGS_CHANGED、SETTINGS_WRITE_FAILED、HOST_CHANGED、EXECUTION_FAILED。所有 UI 文案按代码生成，不存储或输出原始 error、页面内容、设置值或插件日志。

成功只证明当前配置下第一页执行及结构校验通过，不证明数据实时、价格正确或协议业务可用。网络请求和 KV 写入仍可能产生声明范围内的副作用；只在安装已批准且配置保存 / 用户验证后执行，不无限自动重试。

## 4. 安全与并发算法

1. 原生确认完成后检查 installed；拒绝、关闭、取消或提交失败直接结束。
2. 为本次已批准包建立新记录；使同 id 的旧记录失效。
3. 开始验证时检查容量与重复运行，冻结本轮 requestId / hash，进入 running。
4. 后台在共享 lease 内重新读取安装状态与摘要；任何变化都在加载 JS 前拒绝。
5. 主线程快照宿主依赖，同时覆盖 EVM Sign 与 NEAR NearSign 为拒绝，关闭 Log；不使用普通 UI runner。
6. 执行清单第一页，使用既有 Runner.Page 校验返回数据，不向 agent 传回页面或异常原文。
7. Close runtime 并释放 lease；主线程核对记录身份、取消标记、当前摘要、启用状态及退出状态，然后写入安全结果并更新绑定同一 requestId 的创建流程通知。
8. 后台工作无论成功、失败或失效，都回收并发槽位。设置、卸载、包更新及网络变化使旧记录失效；取消标记还阻止尚未开始的工作执行。

## 5. 任务拆分与测试规格

每个工作块小于四小时，依次完成：定义元数据与状态机；共享禁签名执行器；接入原生批准与设置 / HTTP 保存；显示状态和重试；回归、race、生产构建及原生窗口检查。先编写下列失败测试，再实现对应行为。

| 场景 | 必须证明 |
| --- | --- |
| 无设置的 ACP / HTTP 提议 | pending 无执行；原生批准后自动检查第一页；passed 绑定包与任务 |
| 有普通 / 秘密设置 | 安装后等待；成功保存后才执行；允许手动验证可选设置 |
| 模块 / 页面失败 | 显示 failed，安装保留；不误报 passed；可以重试 |
| EVM / NEAR 签名，含模块顶层 | 验证期间始终拒绝，两种钱包批准回调均不触发 |
| 随机秘密值写入异常和 host.log | 元数据、创建反馈及验证日志不包含秘密值 |
| 设置部分失败 / 清除秘密 | 旧通过状态和完成时间失效；均不自动执行；清除秘密后仍能手动验证 |
| 同 id 重复点击 | 仅一个后台工作，UI/API 执行 lease 不可绕过 |
| 五个活动工作及第六个 | 容量有界，失败与失效工作释放槽位，可再试 |
| 未开始的验证后卸载 / 更新 | 不执行过期版本，也不把新包验证结果写入旧任务 |
| 已完成但主线程通知迟到 | 设置、更新、卸载和宿主变化后的旧结果被丢弃 |
| 禁用、无导航、破坏完整性 | 不执行，不自动启用，不错误标记通过 |
| 新建另一生成任务 | 旧安装结果不覆盖新任务的进度或通知 |
| 重启 | 无旧状态 / 无自动执行；已安装应用仍可正常打开 |
| UI 状态与既有 HTTP 响应 | 状态、时间和重试入口可见；兼容已有直接 page JSON 与安装状态 |
